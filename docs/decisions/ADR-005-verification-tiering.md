# ADR-005: 验证分层 —— 预览 / PR / main 兜底三层

- 状态：已接受
- 日期：2026-09-22
- 来源：TokenStore ci-smoke-tiering（2026-09-22 交付，PR #99；负责人裁定「pr 不跑冒烟，只在 main 上跑，跑出问题立即修复就行」）+ `make web-dev` 快速预览（l1-micro）

## 背景

TokenStore 实测痛点：全量行为冒烟（396+ 断言）同时挂在三个位置——本地 Accept 四门、每个 PR 的 CI、每次 main push——导致：

- 每个小代码改动的 PR 反馈 ~18 分钟，吞吐瓶颈是等冒烟而不是写代码；
- `pr-merge` 默认超时 900s < 17min 冒烟，每次合入必超时、人工 re-arm（真实摩擦，反复发生）；
- 开发期「改一行页面看效果」被迫走准出门禁（typecheck+lint+test+build 全家桶），秒级预览通道存在（dev server HMR）却没接进工作流。

教训归纳：**把最重的行为验证放在了迭代最频繁的位置**。

## 决策

验证按「反馈速度 × 置信要求」分三层，**预览快、门禁严，两层不混**：

| 层 | 位置 | 内容 | 速度 | 定位 |
|----|------|------|------|------|
| L0 预览 | 开发者本机 | dev server HMR / 单元测试 / 定向脚本 | 秒级 | 迭代反馈，非准出 |
| L1 PR | CI（pull_request） | 静态门禁 + 单元测试 + 约定检查 | ~2min | 合入前底线 |
| L2 兜底 | CI（push main） | 全量行为冒烟 | 分钟级 | 发布点行为验证 |

配套原则：

1. **行为冒烟只挂 main push**——合入点即发布点（TokenStore：同一次 push 触发镜像构建）。PR 层不跑冒烟，省下的等待是纯收益。
2. **main 冒烟挂了 = 立即修复流程**：修复 PR → 合入 → main 全量复验绿。不人为制造失败演示，流程写进项目 playbook 即可。
3. **本地 Accept 四门不缩水**——PR 免冒烟的前提是合入前行为验证仍在（本地跑），CI 只是把重复的那份后置。若项目连本地四门都免掉，就裸奔了，本 ADR 不允许。
4. **预览层与准出门禁分立**：开发期看效果用 dev server（`web-dev` 类目标：幂等起栈 → 直连 dev server）；准出仍走全量 check。不因为「预览也要跑一遍 build 才放心」把两层混回去。
5. **`pr-merge` 超时 ≥ 项目最慢 PR job**；最慢 job 超过几分钟时，正确动作不是反复 re-arm，而是把该 job 按本 ADR 后置到 main push。

## 后果

- 坏改动可能在 main 冒烟才暴露（PR 层零行为验证），需回滚 PR 修复——用「晚发现」换「快迭代」；TokenStore 已评估并接受（长尾冒烟节与日常改动代码面交集小）。
- 合入点从「人盯着等冒烟绿」变为「合入后 ~几分钟自动知道结果」，合并动作本身变快。
- 本地与 CI 冒烟环境须同构（否则 main 兜底抓的是环境差而非缺陷——TokenStore PR #96 的容器拓扑修复即是此前提）。
- 分层参数（PR 层具体跑什么、main 层跑哪些冒烟）是项目填充物，写在项目 `product-pipeline.md` 附录；引擎只定三层结构与原则。
